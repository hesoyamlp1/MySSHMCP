# im-hub 设计（飞书这一半）

写于 2026-09-08。**这是设计稿，等用户点头再动手写代码。**

## 一、要解决什么

别人在飞书里给陆晟提的事，一条都不漏。

不是"能读飞书消息"——那个昨晚已经验证能做了。是**别人提的事不会因为他当时没看群而丢掉**。

判断标准：他问一句"最近有谁给我提了什么"，能拿到一份靠谱的清单，包括他睡觉时发生的。

## 二、数据从哪来

昨晚验证过的两条通路：

| | 覆盖范围 | 实时性 | 代价 |
|---|---|---|---|
| 用户身份（`lark-cli --profile mori --as user`） | 他所在的**全部** 36 个会话 | 无推送，只能定时拉 | 无 |
| 机器人身份（长连接） | 只有 Mori 被拉进的群（现在 1 个） | 秒级推送 | 群里同事看得见多了个机器人 |

**这一版只用用户身份**。理由：覆盖全，同事无感知，不需要往 20 个工作群里塞机器人。代价是有延迟，但收需求这件事不需要秒级。

机器人那条通路保留（长连接进程还跑着），以后某个群真需要秒级响应时再把 Mori 拉进去，采集侧不用改。

## 三、存什么

VPS 上一个 SQLite：`~/.mori/im/feishu.db`。三张表。

**messages** — 原始消息，一条不改地存

    message_id      主键，飞书的 om_xxx
    chat_id         哪个会话
    chat_name       会话名（冗余存一份，改名了也能看懂历史）
    sender_id       发送者 open_id
    sender_name     发送者名字
    create_time     发送时间（毫秒时间戳）
    msg_type        text / post / image / interactive / …
    content         正文（已渲染成人能读的文本）
    mentions        @了谁（open_id 列表，JSON）
    at_me           是不是 @ 了陆晟（0/1，查询最常用，单独存一列）
    is_mine         是不是他自己发的（0/1）
    thread_id       线程 id，回复才有
    parent_id       回复的哪条
    raw             lark-cli 返回的原始 JSON，留着以防解析漏了字段

**watermarks** — 每个会话读到哪了

    chat_id         主键
    last_time       最后一条的时间戳
    last_message_id 最后一条的 id（同一毫秒多条时用来去重）
    last_sync_at    上次采集时间
    error           上次采集的报错（连续失败要能看出来）

**chats** — 会话名单和监控开关

    chat_id / name / chat_mode(group|p2p) / monitored(0|1) / note

### 为什么存原始消息而不是"判断后的需求"

采集这一步**一次模型调用都不做**。理由：

- 采集要能长期无人值守地跑，掺进模型调用就有成本、有失败模式、有判错。
- 判断"这算不算给我提的需求"需要上下文（这个群平时在聊什么、这个人和他什么关系），采集时没有；他问的时候由会话里的模型来判，判得准得多。
- 判错了可以重判，原始消息在那不会变。

## 四、对外提供什么

一个 MCP 服务，跟 ssh-hub / browser-hub / computer-hub 同一个模子：VPS 上 systemd 常驻，Claude Code 和 codex 都能连。工具控制在四个：

**`im_inbox`** — 上次之后有什么新的
- 参数：`since`（时间或"上次问之后"）、`only_at_me`、`chat`（限某个会话）、`limit`
- 返回：按会话分组的新消息，每条给发送者、时间、正文、有没有 @ 他
- 这是最常用的一个

**`im_messages`** — 读某个会话的一段消息
- 参数：`chat`（名字或 id）、`since` / `until` 或 `last_n`
- 用途：他说"图搜产品群昨天在聊什么"

**`im_search`** — 跨会话搜
- 参数：`query`、`sender`、`chat`、时间范围
- 本地库里搜（快、离线）；库里没有的更早历史再回落到飞书接口

**`im_chats`** — 列会话、开关监控
- 看有哪些会话、哪些在监控、每个上次同步到什么时候、有没有连续失败

### 不提供的

- **不发消息。** 发消息走现有的 `lark-cli`，我判断该不该发；hub 里不放这个能力，避免误触发。
- **不主动推送、不注入会话。** 用户 2026-09-08 明确要按需查询。
- **不做需求状态机。** 第一版只做"看得见"。等实际跑几天，看真实的需求长什么样，再决定台账怎么设计。这一条是刻意留白，不是遗漏。

## 五、怎么跑

代码进 MySSHMCP 仓库，TypeScript，跟另外三个 hub 一样的形态：

    mcp-ssh-pty --im-hub --http --port 27795     # MCP 服务，systemd 常驻
    mcp-ssh-pty --im-sync                        # 采集一轮，给定时任务用

采集一轮做的事：对每个监控中的会话，用水位之后的时间去拉，写进库，更新水位。8 个会话大约 8 次接口调用，几秒。

定时任务由用户自己按需开（他 2026-09-08 说的），不默认装。建议间隔 10 分钟。

**凭证**：沿用 `~/.mori/feishu/mori.env` 里的 Mori 应用，`--profile mori`。用户身份的令牌由 lark-cli 自动续，满一年要重新扫码，到期前会在 `im_chats` 里报出来。

## 六、边界

- **只覆盖飞书，也就是恩阅科技那边。**同程的事在企业微信里，这一版不碰。两边的内容不互相输出——2026-09-08 已经因为这个出过一次错（把同程的项目清单报给了恩阅的同事）。
- **读不到他入群前的消息**，取决于每个群「新成员可查看历史」的设置。
- **保密群读不到**，附件也下不了。
- **卡片消息**拿到的是结构化 JSON，要另外解析才好读；第一版原样存着。

## 七、要用户定的

1. **采集间隔**：默认建议 10 分钟。
2. **消息留多久**：默认建议留 90 天，之后自动删。库大概每月几十兆。
3. **单聊要不要全收**：现在只有陈凌晨在说话，但以后别人私聊他也是需求来源。默认收全部真人单聊，机器人单聊不收。
